# SKB Knowledge Continuity Contract

Canonical knowledge base: `soobujmiah/skb`.
Canonical SKB entry point: `AGENT_NAVIGATION.md`.

## Session start

For any non-trivial work, consult the minimum relevant owner/project context from SKB before making material decisions. The user does not need to repeat “read SKB” for every later session on this repository.

Use this order:

1. repository-local AI instructions and current state;
2. SKB `AGENT_NAVIGATION.md`;
3. minimum sufficient relevant SKB context;
4. current repository evidence, tests, CI, and device evidence.

SKB is a continuity/context layer. It does not override repository-local rules, direct implementation evidence, higher-priority policy, or explicit human authority.

## Session close

Before handoff, perform a Knowledge Return Review. Identify durable facts, decisions, architecture changes, constraints, capabilities, failures, and verification evidence that may be useful to SKB. Classify each as new, update, duplicate, contradiction, historical, uncertain, or rejected. Do not return secrets, private payloads, temporary noise, or unsupported claims.

## Adaptive engineering

No fixed language, framework, architecture, document set, or project template is mandatory. Select the best-fit implementation and documentation structure from the actual requirements and constraints.

## Failure handling

If SKB cannot be reached, do not invent its contents. Continue from verified repository evidence when safe and record the missing knowledge dependency.

Legacy Mode is intentionally deferred and is not part of this contract.
